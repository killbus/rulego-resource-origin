# Origin 自有资源回收闭环

状态：三审整合 v3 已完成实施及 A1–A7 验收。最终源码 804d88e 通过独立定向测试及 GitHub CI 36604788001（Linux unit/race、双架构固定运行时、SIGKILL 恢复）。完整证据与限制见 research/completion-audit.md。任务 ID 保持 resource-lifecycle-gc。

## 目标
让 origin 对自己管理的 ready、trash、staging 和 catalog 完成从生产到回收的生命周期，避免终态元数据和可识别残留随历史资源 ID 永久累积；不误删活跃资源或新 generation。

## 事实与边界
- 2026-09-29 检查基线 b22d4b8，包含 trash 恢复修复。生产部署版本未确认。
- ready 按 TTL 退役，trash/staging 删除与 catalog 持久化已有独立重试；catalog JSON 与内存终态记录目前没有淘汰。
- 当前有启动核对，缺少周期性残留发现；外部迟到生产者可以重建旧 staging。
- origin 管发布状态和自有目录；producer 管生产与取消；原生 resource_mapping 管 HTTP 字节传输。
- maxRetainedBytes 保留有效 ready 逻辑容量语义。它不代表真实磁盘占用。

## 范围与需求
R1. 回收已完成恢复工作的 expired/failed catalog JSON 及内存记录。必须确认当前 generation、相关 payload 已清理、无待处理持久化/删除工作、本代 waiter 已交付；不以 pending 子引用阻止父终态回收。
R2. 在无新请求时周期发现可证明归 origin 所有的历史残留，并交给现有回收机制处理。覆盖旧 generation staging、trash、无有效发布记录的 ready；包括 catalog/.record-*；独占受管目录内的废弃条目纳入清理，异常路径不得跟随到根外。
R3. 清理过程具备幂等重试、并发代际隔离、进程崩溃恢复、有限扫描批次和可诊断的积压；避免新增第二套独立垃圾回收框架。
R4. 保持现有发布、TTL、父子依赖及原生 HTTP 行为；明确终态元数据删除后 Resolve 状态变化。
R5. 用独立反例、修复前失败和真实运行边界验证行为，保留既有失败记录与证据限制。

## 已确认行为
- 保持绝对 TTL；本期不新增播放续期，也不因磁盘压力提前淘汰未过期 ready。
- 终态在 payload 清理、持久化责任及本代 waiter 交付完成后立即进入 GC，不设人为保留期或保留期配置。立即表示下一可调度清理机会；失败时退避重试。
- 删除终态 catalog 后，Resolve 从 expired/failed 变为 not_found；过期响应对应从 410 变为 404。未知与已回收 ID 不再永久区分。
- 同 ID 再次 Acquire 允许新 generation；旧 token 始终不能提交/失败新 generation。
- 健康、有限输入下，扫描和清理最终完成；永久权限故障或持续迟到写入下只承诺安全重试和诊断，不承诺固定时间清空或硬容量上限。

## 验收
A1 / R1：批量生成不同 ID，进入终态并完成回收，磁盘 catalog 与内存记录均被释放；GC 完成后为 not_found，不依赖推进额外保留期。
A2 / R1,R3：catalog 删除失败、重启及同 ID 新 generation 插入不造成旧工作删除新 catalog、恢复过期内容或丢失待清理责任。
A3 / R2,R3：停止请求流量后，历史残留仍被发现并清除；活跃 staging、未过期 ready、符号链接目标保持安全；独占受管目录内未知名字不形成永久垃圾。
A4 / R2,R3：在扫描观察、认领、删除之间插入 Acquire/Commit、迟到写入、部分删除失败、重启，不能误删新代；隔离后的残留在重启后仍可发现。
A5 / R3：扫描按批推进，重复失败不形成忙循环；慢递归删除不持有发布锁；记录待清理数量、最老等待时间和失败类别，且不对每个文件做无限日志输出。
A6 / R4：既有发布、代际 token、父子依赖、等待者、ready 字节计数及原生 HTTP 回归通过；在有限输入/健康文件系统下无永久元数据保留环。
A7 / R5：能比较旧版的行为测试在未修改基线上因目标断言失败，在候选版通过；独立检查者执行测试并提出反例。环境错误、编译错误和无关 teardown 失败不计作目标缺陷复现。

## 范围外
播放会话/租约、播放器逻辑、新 HTTP 服务、FFmpeg 取消机制修改、预留额度与整盘配额、磁盘压力准入/LRU、永久历史查询、掉电级持久性升级。此次不把 canceled 日志认定为 trash 回归。部署、发布与生产删除不属于规划交付。

## 决策与前提
用户确认：无保留期、.record-* 纳入本期、回滚按旧规则执行。单个根只能有一个活跃 manager；owner 标记不是进程锁。重启沿用 pending→abandoned，仅有效 ready 恢复发布。

## 交付组织
本期按单个协调任务管理两个紧耦合部分：终态回收、残留核对；共享恢复/所有权契约先定稿，统一独立验收。暂不创建容量和播放子任务。若后续拆子任务，残留核对必须显式依赖终态回收的缺失记录判定规则。
